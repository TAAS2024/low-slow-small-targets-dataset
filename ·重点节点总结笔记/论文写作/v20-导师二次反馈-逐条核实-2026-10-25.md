## 1. 决定性证据：他的 PDF 字体子集损坏

Appendix A.1 原文（docx 逐字，p153）：

> Implementation revision (boundary harmonisation). The initial build replaced host background over the entire feather band, carrying residual high-frequency texture into the ring around the target (approximately three times the local background energy). The correction of Section 3.2 **restricts that replacement appropriately; applied offline to the identical 300 conditioning points**, it lowers both downstream proxy rates (any-class 0.650 to 0.620; R_aerial 0.557 to 0.520; paired McNemar p = 0.14 …)

导师收到的是：

> 3.2 **rets tht rlment apropriatly aplid flln th idntial 30 onditionin points**

逐词对齐后，丢失的字符是：

| 原文 | 他看到的 | 消失的字符 |
|:--|:--|:--|
| restricts | rets | s, t, r, i, c |
| that | tht | a |
| replacement | rlment | e, p, a, c, e, e, t |
| appropriately | apropriatly | p, e |
| applied | aplid | p, e |
| offline | flln | o, i, e |
| the | th | e |
| identical | idntial | e, i, c, a |
| **300** | **30** | **0** |
| conditioning | onditionin | c, g |

**「300」变成「30」是决定性的。** 数字 0 都被吞掉，说明这不是 OCR 误识、不是渲染成豆腐块、不是文本抽取顺序错乱，而是 **PDF 字体子集的 ToUnicode CMap 把一批字形映射到了空**。文档在屏幕上看着「正常」，只是字母凭空消失。

同一个故障可以完整解释另外 4 项：

- [21] `freebies` → `frebless`：`ie` 两个字形被映射错位
- [31] `using textual inversion` → `using text-to-image generation`：整段字形映射到错误的码位，取出来是邻近字符串
- Eq.(5) 的 `'`、Eq.(16) 的 `−`：单字符优先被吞，因为它们不在正常英文词里

**建议他向导出 PDF 的工具要一份字体嵌入正常的版本，或者直接看 docx。** 这是唯一能一次性消掉 5 项的改动。

## 2. 5 项「docx 正确」的原文照抄

### Eq. (5) — 撇号在

OMML 对象第 5 个，`m:t` 逐字读出：

```
c=ConcatEcannyIbg,D'
```

末尾撇号为 ASCII `U+0027`，与 Eq.(1) `D'x,y=` 中的撇号**是同一个字符**。导师说 Eq.(1)(2) 显示正常而 Eq.(5) 没有撇号——同一份文档里同一字符不可能一个渲染一个不渲染，这只能是他的提取链路在 `D')` 这个位置把 `'` 吞了（后面紧跟右括号）。

Eq.(1)：`D'x,y=d,  ifx,y∈M | Dx,y,  otherwise`
Eq.(2)：`S'x,y=cfg,  ifx,y∈M | Sx,y,  otherwise`

### Eq. (16) — 负号在

```
H=-ipilog2pi
```

`H` 之后紧跟 `-`（ASCII `U+002D`），随后是 `Σ`（`i` 为上下限占位）`p_i log₂ p_i`。

### [31] — 标题与会议信息完全正确

docx p209 逐字：

> [31] R. Gal, Y. Alaluf, Y. Atzmon, et al., An image is worth one word: Personalizing text-to-image generation using **textual inversion**, in: **Int. Conf. Learn. Represent. (ICLR)**, 2023. https://arxiv.org/abs/2208.01618.

导师说应为 "using Textual Inversion"、会议应为 ICLR——**docx 里就是这样，一个字不差**。他看到的 "using text-to-image generation" 重复，是字形映射错位。

### [21] — 拼写正确

docx p199 逐字：

> [21] C.-Y. Wang, A. Bochkovskiy, H.-Y.M. Liao, YOLOv7: Trainable **bag-of-freebies** sets new state-of-the-art for real-time object detectors, in: Proc. IEEE/CVF Conf. Comput. Vis. Pattern Recognit. (CVPR), 2023, pp. 7464–7475. https://arxiv.org/abs/2207.02696.

### Appendix A.1 — 完整可读

见 §1 原文。用 LibreOffice 独立渲染后 `pdftotext` 提取，该段同样完整：

> The correction of Section 3.2 restricts that replacement …

即**换一个渲染器就不乱码**，进一步排除文档本身的问题。

## 5. 未采纳的两项建议，及理由

导师建议「确认 Eq.(5) 是 D′ 不是 D」「确认 Eq.(16) 有负号」。这两处**不需要改**，因为 OMML 里本来就有；改的收益为零，风险却非零。

另外考虑过把 `'`（U+0027）统一换成 `′`（U+2032）、把 `-`（U+002D）换成 `−`（U+2212），以提高跨渲染器鲁棒性。**最终决定不做**，原因是减号替换有实质风险：

OMML 里 17 处 ASCII `-` 中有 **6 处是下标的连字符，不是减号**：

```
[8]  xt-1 = m⊙xt-1 + 1-m⊙xt-1bg      ← x_{t-1}，t-1 是下标
[14] θk-1                            ← θ_{k-1}，k-1 是下标
```

无差别替换会把下标里的 `t-1` 变成 `t−1`（减号符号），公式语义直接写错。正确做法需要逐个判断 XML 结构（是否位于 `m:sSub` 内），而这一步的收益仅仅是「排版更标准」，不改变「负号是否存在」这一事实。用 17 处里可能写错 6 处的风险，换一个审稿人看不出来的规范化，不划算。

## 7. 建议他做的最小核验

不必逐条翻 PDF，两个动作即可：

```bash
# 1. 确认 pdf 的文字层是完好的：任意一句必须能原样搜到
pdftotext 他的版本.pdf - | grep -c "restricts that replacement"

# 2. 确认内嵌图是新版
unzip -p docx word/media/image3.png | sha256sum
# 应为 d5ef7d4882d581a3a462a2dd7c0ab075a8c190d2e9650b2196e380a63b446533
```

第 1 条返回 0，就说明那份 PDF 不能用，后面 5 项指控自动作废。

如果必须交 PDF，导出时勾选**嵌入字体 / PDF/A**；或者干脆交 docx——Elsevier 的 Editorial Manager 接受 docx 源文件。
